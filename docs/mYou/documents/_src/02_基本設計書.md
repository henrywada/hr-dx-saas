## 1. はじめに

### 1.1 本書の目的

本書は、要件定義書（MYOU-RD-001）に定義された要件を実現するための、システム方式・機能構成・画面構成・データ構造・外部インターフェースの基本設計を定義したものである。実装レベルの仕様は詳細設計書（MYOU-DD-001）に定義する。

### 1.2 適用範囲

ミュー株式会社向け製品トレーサビリティ・有効期限管理システム（HR-DX SaaS の製品トレーサビリティ機能）を対象とする。HR-DX SaaS 基盤に共通する認証・権限・レイアウト等の仕組みについては、本システムに関係する範囲で記載する。

## 2. システム方式設計

### 2.1 システム構成

本システムは、クラウド上で稼働する Web アプリケーションとして構築する。専用のクライアントソフトウェアのインストールは不要であり、スマートフォン・タブレット・PC のブラウザから利用する。

```
┌──────────────────────────────────────────────────────────┐
│  利用者端末（スマートフォン／タブレット／PC）             │
│   ・ブラウザ（Chrome / Safari / Edge）                    │
│   ・カメラ（QRスキャン用）                                │
└───────────────────────┬──────────────────────────────────┘
                        │ HTTPS
┌───────────────────────▼──────────────────────────────────┐
│  アプリケーション基盤（Vercel）                           │
│   ・Next.js（App Router）                                 │
│     - Middleware：認証チェック／セキュリティヘッダー付与  │
│     - Server Component：画面描画・データ取得              │
│     - Server Action：登録・更新処理                       │
└──────────┬───────────────────────────────┬───────────────┘
           │ PostgreSQL 接続                │ SMTP
┌──────────▼───────────────────┐  ┌────────▼────────────────┐
│  データベース基盤（Supabase）│  │  メールサーバー（SMTP） │
│   ・PostgreSQL               │  │   ・アラートメール送信  │
│   ・Row Level Security       │  └─────────────────────────┘
│   ・Auth（認証）             │
└──────────────────────────────┘
```

### 2.3 アーキテクチャ方針

| No    | 方針                           | 内容                                                                                                                     |
| ----- | ------------------------------ | ------------------------------------------------------------------------------------------------------------------------ |
| AR-01 | サーバー中心の処理             | データの読み取りはサーバーコンポーネント、更新はサーバーアクションで実行し、データベース資格情報をブラウザへ露出させない |
| AR-02 | 責務の分離                     | 読み取り処理（`queries.ts`）と更新処理（`actions.ts`）をモジュールとして分離する                                         |
| AR-03 | データベースによるアクセス制御 | テナント分離はアプリケーションの条件分岐に依存せず、データベースの RLS で強制する                                        |
| AR-04 | 在庫更新のアトミック化         | 在庫の増減を伴う処理はデータベース関数（RPC）内で行ロックを取得して実行する                                              |
| AR-05 | 入力検証の一元化               | 全ての更新処理の入口でスキーマ検証を行い、不正値をデータベースへ到達させない                                             |
| AR-06 | 日時の統一                     | 日付の生成・判定は日本時間（Asia/Tokyo）を基準とする                                                                     |

### 2.4 処理方式

| 処理区分       | 方式                     | 適用機能         |
| -------------- | ------------------------ | ---------------- |
| オンライン処理 | 画面操作に対する即時処理 | 全機能           |
| バッチ処理     | なし                     | —                |
| 自動通知       | なし（手動送信のみ）     | 有効期限アラート |

> 有効期限アラートは自動送信を行わない。担当者が監視画面を確認し、必要に応じて送信ボタンを操作する運用とする（要件定義書 OS-01 参照）。

## 6. 採番規則・コード設計

### 6.1 ロット番号

```
LOT-YYYYMMDD-NNNN
 │      │        └─ 当日通番（4桁ゼロ埋め、0001 から）
 │      └─────────── 発行日（西暦8桁）
 └────────────────── 固定接頭辞
```

- 例：`LOT-20260729-0001`
- 入荷登録時に QR をスキャンしなかった場合、当日の最大通番＋1で自動採番する
- 通番が5桁以上になった場合も正しく採番できるよう、文字列比較ではなく数値比較で最大値を求める

### 6.2 TraceNo

```
YYYYMMDD-NNNN
   │        └─ 当日通番（4桁ゼロ埋め、0001 から）
   └─────────── 発行日（西暦8桁）
```

- 例：`20260729-0001`
- 出荷登録1件につき1つ採番する

### 6.3 出荷先No（得意先No）

- 施工会社の新規登録時に、テナント内の最大値＋1を採番する
- テナント内で一意（重複不可）

### 6.4 QR コード仕様

#### ロットQR（段ボールに貼付）

```
LOT:<ロット番号>,MFG:<製造日 YYYY-MM-DD>,EXP:<有効期限 YYYY-MM-DD>
```

例：`LOT:LOT-20260729-0001,MFG:2026-07-01,EXP:2026-12-31`

| 項目  | 必須 | 内容                                     |
| ----- | ---- | ---------------------------------------- |
| `LOT` | 必須 | ロット番号                               |
| `MFG` | 任意 | 製造日                                   |
| `EXP` | 任意 | 有効期限（入荷登録画面で確認・修正可能） |

> 上記書式に一致しない QR を読み取った場合は、読み取り文字列全体をロット番号として扱う（手入力ラベル・旧ラベルとの互換のため）。

#### トレーサビリティQR（出荷製品に貼付）

```
https://app.hr-dx.jp/p/myou/trace/<発行ID>?traceNo=<TraceNo>
```

例：`https://app.hr-dx.jp/p/myou/trace/3f6b1c2e-…?traceNo=20260729-0001`

| 設計意図                  | 内容                                                                                                                  |
| ------------------------- | --------------------------------------------------------------------------------------------------------------------- |
| URL 形式の採用            | スマートフォンの標準カメラで読み取った際に、専用アプリなしで案内ページが開くようにするため                            |
| 表示情報を URL に含めない | ロット番号・有効期限等を URL に埋め込むと改ざんによる表示偽装が可能になるため、公開ページ側でデータベースから取得する |
| `traceNo` クエリの付与    | 社内のトレーサビリティ検索で、同一の QR を再スキャンして照会できるようにするため                                      |

> 旧書式（`LOT:…,ShipTo:…,TraceNo:…,QTY:…,EXP:…`）で発行済みの物理ラベルも、社内のトレーサビリティ検索で引き続き読み取れる。

### 6.5 ラベル印字項目

トレーサビリティQR ラベルには、QR コードとあわせて以下を印字する。

| 項目       | 内容               |
| ---------- | ------------------ |
| ロット番号 | 引当元のロット番号 |
| TraceNo    | 発行された TraceNo |
| 出荷先No   | 施工会社の出荷先No |
| 出荷数量   | 当該出荷の本数     |
| 有効期限   | ロットの有効期限   |

> 缶単位で複数枚のラベルが必要な場合は、印刷部数を指定して同一内容の QR を複製印刷する（既定値は出荷数量、上限1,000部）。内容の異なる QR を缶ごとに発行することはしない。

## 7. 権限・メニュー設計

### 7.1 メニュー表示制御

本システムの各画面は、HR-DX SaaS のサービスメニュー管理機構により表示制御される。

| テーブル           | 役割                                                                 |
| ------------------ | -------------------------------------------------------------------- |
| `service_class`    | サービスカテゴリの大分類                                             |
| `service_category` | サイドメニューに表示する分類（本システムは「製品トレーサビリティ」） |
| `service`          | 個々の機能（画面）の定義と遷移先 URL                                 |
| `tenant_service`   | テナント単位で有効な機能                                             |
| `app_role_service` | 役割単位で有効な機能                                                 |

メニューは `tenant_service` と `app_role_service` の **両方** の条件を満たす機能のみ表示する。

### 7.2 アクセス制御方式

| 階層         | 制御内容                                                                                         |
| ------------ | ------------------------------------------------------------------------------------------------ |
| Middleware   | 未認証アクセスをログイン画面へリダイレクトする                                                   |
| サーバー処理 | 全ての読み取り・更新処理の冒頭でログインユーザーとテナントを取得し、未取得の場合は処理を中断する |
| データベース | RLS により、自テナント以外の行を読み書きできないようにする                                       |

## 8. 外部インターフェース設計

### 8.1 メール送信インターフェース

| 項目     | 内容                                                  |
| -------- | ----------------------------------------------------- |
| 用途     | 有効期限アラートの通知                                |
| 方式     | SMTP（Nodemailer 経由）                               |
| 送信契機 | 担当者による「アラート送信」ボタン操作                |
| 宛先     | 施工会社マスタに登録されたメールアドレス              |
| 件名     | `【重要】製品有効期限に関するお知らせ（{会社名}様）`  |
| 本文     | 対象製品の一覧（ロット番号／数量／有効期限／TraceNo） |
| 送信結果 | 成否をアラート送信履歴へ記録する                      |

### 8.2 公開ページインターフェース

| 項目       | 内容                                                            |
| ---------- | --------------------------------------------------------------- |
| 用途       | 施工会社・現場作業者による製品情報の確認                        |
| URL        | `/p/myou/trace/{発行ID}`                                        |
| 認証       | 不要                                                            |
| 表示項目   | ロット番号、施工先No、トレースNo、有効期限、販売元（社名・URL） |
| 非表示項目 | 出荷先の会社名、担当者名、数量、在庫情報など、業務上の機密情報  |
| 該当なし時 | 「見つかりません」ページを表示する                              |

### 8.3 QR 読み取りインターフェース

| 項目       | 内容                                                            |
| ---------- | --------------------------------------------------------------- |
| 方式       | 端末のカメラを利用したブラウザ内スキャン                        |
| 前提       | ブラウザのカメラ使用許可、HTTPS 接続                            |
| カメラ選択 | 背面カメラを優先。前回使用したカメラを記憶する                  |
| 代替手段   | QR を読み取れない場合、ロット番号・TraceNo の手入力を可能とする |

## 9. 運用設計

### 9.1 運用体制と業務サイクル

| 業務             | 頻度         | 担当       | 内容                                         |
| ---------------- | ------------ | ---------- | -------------------------------------------- |
| 入荷登録         | 納品都度     | 入荷担当者 | ロットQR をスキャンし数量を登録              |
| 在庫確認         | 受注都度     | 出荷担当者 | 有効期限の近い在庫を優先して引当             |
| 出荷登録         | 出荷都度     | 出荷担当者 | 出荷先・数量を指定して登録、QR を印刷・貼付  |
| 有効期限監視     | 週次（推奨） | 管理担当者 | 監視画面を確認し、必要に応じてアラートを送信 |
| 使用数の更新     | 報告都度     | 管理担当者 | 施工会社からの報告に基づき使用数を更新       |
| 納入先マスタ保守 | 随時         | 管理担当者 | 新規取引先の登録、メールアドレスの更新       |

### 9.2 ログ・監査

| 種別                   | 記録内容                     | 保管場所               |
| ---------------------- | ---------------------------- | ---------------------- |
| 画面アクセスログ       | 全 GET リクエストの閲覧記録  | `access_logs` テーブル |
| 出荷操作の記録         | 登録担当者名、登録日時       | `myou_delivery_logs`   |
| アラート送信ログ       | 送信日時、送信先、対象、成否 | `myou_alert_logs`      |
| アプリケーションエラー | サーバー側のエラー内容       | ホスティング基盤のログ |

### 9.3 バックアップ・復旧

| 項目             | 方針                                                                  |
| ---------------- | --------------------------------------------------------------------- |
| バックアップ     | データベース基盤（Supabase）の自動バックアップ機能に準拠する          |
| 復旧             | 障害時は基盤のバックアップからリストアする                            |
| アプリケーション | ソースコードは Git リポジトリで版管理し、いつでも再デプロイ可能とする |

### 9.4 リリース方式

| 項目             | 内容                                                                                 |
| ---------------- | ------------------------------------------------------------------------------------ |
| デプロイ         | Git リポジトリへの反映を契機に、ホスティング基盤（Vercel）が自動ビルド・デプロイする |
| データベース変更 | マイグレーションファイルによる版管理とし、適用順序を保証する                         |
| 本番ドメイン     | `https://app.hr-dx.jp`                                                               |

## 10. 移行設計

### 10.1 データ移行

| 対象               | 移行要否 | 方針                                                           |
| ------------------ | -------- | -------------------------------------------------------------- |
| 施工会社（納入先） | 要       | 運用開始前に、取引先の会社名・メールアドレスを画面から登録する |
| 在庫               | 要       | 運用開始時点の在庫を、ロット単位で入荷登録する                 |
| 過去の出荷履歴     | 不要     | 運用開始以降の出荷から記録を開始する                           |

### 10.2 運用開始手順

| 順序 | 作業                                           | 担当           |
| ---- | ---------------------------------------------- | -------------- |
| 1    | 利用者アカウントの発行、役割の割当             | システム管理者 |
| 2    | 施工会社（納入先）マスタの登録                 | 管理担当者     |
| 3    | メールアドレスの登録確認（アラート利用のため） | 管理担当者     |
| 4    | 期首在庫の入荷登録                             | 入荷担当者     |
| 5    | 在庫一覧による登録内容の確認                   | 管理担当者     |
| 6    | 試験出荷によるトレーサビリティQR 印刷の確認    | 出荷担当者     |
| 7    | 本番運用開始                                   | 全員           |

### 10.3 教育・習熟

| 対象者           | 教育内容                                           | 資料                           |
| ---------------- | -------------------------------------------------- | ------------------------------ |
| 入荷・出荷担当者 | 入荷登録、在庫確認、出荷登録、QR 印刷              | 操作マニュアル（ユーザー向け） |
| 管理担当者       | マスタ保守、有効期限監視、アラート送信、使用数更新 | 操作マニュアル（管理者向け）   |
| システム管理者   | アカウント管理、権限・メニュー設定                 | 操作マニュアル（管理者向け）   |

> 各画面にはヘルプボタンを配置し、操作要点をその場で確認できる。あわせて、システム内の「資料一覧」からシステム仕様書を閲覧できる。
